# 終了・応答停止対策と検証（0.5.2）

2026-09-13。versionCode 13、applicationId `io.github.hatake716.pixelcity`。

## 実機の終了記録から分かったこと

8 GBのPixel 10aの終了履歴で、0.5.1が2026-09-13 01:24:55にANR（応答なし）で終了していた。入力イベントへの応答が5,001 ms間返らず、ANR時のメインスレッドは `GameView.drawToolbar → PixelCanvas.set → Canvas.drawRect` を実行していた。未解禁の道具を暗くする市松模様を、1ピクセルずつ別の描画命令として送っていた。

当該ANR資料では最大RSS約861 MiB、約5分間の累積Java割当量約10 GB、GC 101回も記録されていた。累積割当量は同時使用量ではない。この記録から直接確認できた終了原因はANRであり、OutOfMemoryErrorやOSによるメモリ不足終了を確認したという意味ではない。

端末の終了・ANR資料と保存データはGit管理外の `artifacts/performance/` に保存し、個人の保存データは同梱しない。

## 変更

- 未解禁ボタンの市松模様を2×2ピクセルの繰り返しシェーダーで描く。色・位置・透明な部分を維持し、1領域につき1描画命令にする。パレットバッファを使う既存のプレビュー描画は維持。
- 建物・車・歩行者・記念建築は、カメラ倍率と端末画面への拡大率を合わせた実表示寸法に応じて1/2、1/4、1/8、1/16で読み込む。拡大時は必要な解像度を読み直す。元画像の寸法・接地点を保持し、配置や透明部分による建物選択が変わらないようにする。
- 建物画像の共有キャッシュを、アプリのJavaヒープ上限の1/8（8〜32 MiB）に制限。従来は88 MiB固定。地面は表示に必要な大きさで生成し、各レンダラーのキャッシュを8 MiBに制限。地形編集の地形用画像も表示寸法で生成する。
- 画面から離れたレンダラーの地面・素材キャッシュ、バックグラウンド移行時やOSのメモリ要求時の画像キャッシュを解放。Androidが描画中の画像を強制的に `recycle()` せず参照だけを外す。都市の状態や選択用の描画順序は保持。
- 惑星メッシュの頂点数を先に数え、必要な配列を1度だけ確保。配列の倍増・最後の全量コピー・各頂点の可変長引数配列を廃止。頂点・詳細地形・写真の解像度は維持。
- GPUへの頂点転送は256 KiBの作業領域を使い回す。従来は再構築ごとにメッシュ全体と同じ大きさのダイレクトバッファを追加確保していた。通常の地球だけで約16.5 MiBある。惑星画面の切替で描画スレッドが終了した後、旧メッシュへの参照を外す。
- 惑星を閉じる・アプリを離れる際に、GLコンテキストが有効な描画スレッドでGPUバッファ・テクスチャ・シェーダープログラムを明示的に削除する。休止中のEGLコンテキスト保持も解除。復帰時に必要な地形・写真を再構築する。画像縮小と転送用配列の改善だけでは残っていた、画面切替ごとのネイティブメモリ増加を解消した。
- 早送りで1フレームにまとめて計算する月数の上限を4から1に変更。処理の遅れを一気に取り戻そうとして操作を長時間止めることを抑える。市政・交通・災害の月次計算式は維持。処理の重い都市では、早送りの実時間あたり進行速度が設定倍率に届かない場合がある。

実装上の判断に使用したAndroid公式資料：

[ビットマップメモリ管理](https://developer.android.com/topic/performance/graphics/manage-memory)、

## 同じ負荷での比較

Android 15 / API 35、1080×2400の同一エミュレーターで、0.5.1の保存済みAPKと0.5.2を比較。新規の自然な512×512地球、人口0、時間停止、交通タブの未解禁ボタンが見える条件を使用。都市と惑星を6往復し、13地点のプロセスPSSを採取。強制GCは使っていない。

| 指標 | 0.5.1 | 0.5.2 | 減少率 |
|---|---:|---:|---:|
| 都市画面1回の四角形描画命令 | 17,872 | 101 | 99.4% |
| 描画処理時間の中央値 | 27.71 ms | 10.31 ms | 62.8% |
| 初回都市画面のPSS | 212.17 MiB | 130.12 MiB | 38.7% |
| 6往復中の最大PSS | 361.75 MiB | 171.30 MiB | 52.7% |

描画時間はソフトウェアCanvasで16回描き、最初の4回を除いた12回の中央値。GPUのフレーム時間や実機FPSを表すものではない。PSSは共有メモリを按分したプロセス使用量で、上記実機ANRのRSSと直接比較しない。採取時点の最大であり、一瞬のピークを全て捉えた数値ではない。

計測コード：`PerformanceProbeTest`。比較資料：`artifacts/performance/performance-baseline.json`、`performance-optimized.json`、対応するPNGと実行ログ。ボタンが実際に未解禁であること、修正前が10,000命令超、修正後が500命令未満であることもテストする。

## 画面切替でのメモリ増加の追加確認

最初の画像縮小・頂点転送改善後でも、30往復ではPSSが単調に増え、最大725.84 MiBに到達した。Javaヒープは約70〜80 MiBなのに、ネイティブヒープが増えていた。GPU資源の明示的な解放とEGLコンテキストの休止中保持解除を追加し、同じ30往復を再実行した。

- 解放修正前：最大743,258 KiB、30往復後743,258 KiB。
- 解放修正後：最大182,344 KiB（178.07 MiB）、30往復後172,677 KiB（168.63 MiB）。
- 修正後の終盤10往復はほぼ165〜168 MiBで推移。30往復、67.562秒を終了・ANRなく完走。
- 初期描画から61地点のPSSを採取。強制GCは使用していない。
- 比較対象はこの作業中の中間版と最終版。同じ30往復で0.5.1を測定した数値ではない。

資料：`performance-stress.json`、`performance-gl-stress.json`、`gl-stress.log`。回帰テストには、都市へ戻った時のPSSが初回復帰時より64 MiB以上増えたら失敗する条件も追加した。
